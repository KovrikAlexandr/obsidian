## Бизнес процессы

Система Mattermost поддерживает процессы корпоративного взаимодействия и обмена информацией внутри организации. Основные бизнес-процессы можно описать следующим образом:

1. **Организация коммуникации в команде**  
   Пользователи объединяются в команды и каналы для ведения переписки. В рамках каналов осуществляется обмен сообщениями, обсуждение рабочих вопросов и координация действий.

2. **Обмен информацией и файлами**  
   Пользователи передают сообщения, файлы и ссылки. Информация сохраняется и может быть повторно использована.

3. **Уведомление участников о событиях**  
   Система уведомляет пользователей о новых сообщениях, упоминаниях и других событиях.

4. **Управление участниками и доступом**  
   Администраторы управляют пользователями, создают команды, настраивают права доступа.

5. **Поиск и доступ к информации**  
   Пользователи выполняют поиск по сообщениям и файлам для получения необходимой информации.

## 2. Общая архитектура программного обеспечения

### Общая характеристика архитектуры

Mattermost — это клиент-серверная система для корпоративного взаимодействия. В неё входят клиентские приложения, сервер, база данных и файловое хранилище.

Центральным компонентом является Mattermost Server. Он обрабатывает запросы клиентов, реализует бизнес-логику, работает с данными и обеспечивает доставку сообщений через REST API и WebSocket.

### Программные компоненты (программная архитектура)

**Web client**  
Работает в браузере, реализован на React. Позволяет пользователю выполнять все основные действия: отправка сообщений, работа с каналами, поиск.

**Desktop client**  
Построен на Electron. По функциональности аналогичен веб-клиенту, но запускается как отдельное приложение.

**Mobile client**  
Реализован на React Native. Обеспечивает работу с системой на мобильных устройствах.

**Mattermost Server**  
Основной компонент, реализующий бизнес-логику. Написан на Go. Обрабатывает запросы, управляет пользователями, каналами и сообщениями, взаимодействует с БД и другими сервисами.

**Database (PostgreSQL)**  
Хранит все основные данные системы: пользователей, сообщения, команды, настройки.

**File storage**  
Используется для хранения файлов. Поддерживает локальное и объектное хранилище (например, S3).

**Search Engine (OpenSearch)**  
Используется для поиска. Хранит индекс сообщений, но не является основным хранилищем данных.

**External identity provider**  
Используется для аутентификации (OIDC, LDAP). Mattermost получает от него данные пользователя.

**Plugins**  
Расширения системы. Позволяют добавлять функциональность без изменения ядра.

## Архитектура данных

#### Общая характеристика

Архитектура данных Mattermost основана на реляционной базе данных PostgreSQL, в которой хранится всё основное состояние системы. Серверная логика работает с данными через модели и слой доступа к данным, отделяя бизнес-логику от хранения.

#### Основные информационные объекты

Ниже кратко описаны основные доменные сущности системы.

**Users**  
Сущность пользователя. Хранит учетную запись, по которой система идентифицирует человека. Здесь находятся логин, email, данные для аутентификации, роли и служебные временные метки. Это одна из центральных сущностей, так как почти все остальные объекты так или иначе связаны с пользователем.

**Teams**  
Сущность команды, то есть рабочего пространства. Команда объединяет пользователей и каналы в рамках одной логической области. Что-то вроде тенанта

**Channels**  
Сущность канала. Канал существует внутри команды и используется как пространство для общения по конкретной теме. Канал связан с командой через `team_id`, поэтому каждый канал принадлежит определённой команде.

**Posts**  
Сущность сообщения. Это основной объект коммуникации в системе. Сообщение связано с пользователем и каналом, содержит текст, временные метки и при необходимости ссылку на корневое сообщение через `root_id`, что позволяет строить треды.

**TeamMembers**  
Сущность участия пользователя в команде. Нужна для того, чтобы отдельно хранить сам факт принадлежности пользователя к команде, а также его роли в рамках этой команды. Это не просто техническая связь, а отдельный объект с собственным смыслом.

**ChannelMembers**  
Сущность участия пользователя в канале. Помимо связи пользователя с каналом, она хранит дополнительные данные: роли, настройки уведомлений, счетчики сообщений и другую служебную информацию. За счёт этого система понимает не только кто состоит в канале, но и в каком состоянии находится взаимодействие пользователя с ним.

**Sessions**  (не БД)
Сущность пользовательской сессии. Используется для хранения информации об активном входе пользователя в систему. Содержит токен, срок действия и связь с конкретным пользователем.

**FileInfo**  
Сущность файла или вложения. Хранит не сам бинарный файл, а его метаданные: идентификатор, владельца, сообщение, к которому он прикреплён, путь к файлу и служебные атрибуты. Это позволяет отделить структурированную информацию о файле от его физического хранения.

**Preferences**  
Сущность пользовательских настроек. Используется для хранения индивидуальных параметров пользователя в виде набора значений формата категория–имя–значение. Через неё реализуются персональные настройки интерфейса и поведения системы.

#### Связи между сущностями

Связи между таблицами реализуются через идентификаторы:
- пользователь связан с командами через `TeamMembers`
- команда содержит каналы через `team_id`
- канал содержит сообщения через `channel_id`
- сообщение связано с пользователем через `user_id`

## 3. Сопоставление функциональной, информационной, программной архитектуры и архитектуры данных

#### Сопоставление функциональной и программной архитектуры

Основные функции Mattermost (аутентификация, управление командами и каналами, обмен сообщениями, поиск) реализуются через взаимодействие клиентских приложений, сервера и вспомогательных компонентов.

Аутентификация выполняется через взаимодействие клиента, Mattermost Server и внешнего OIDC-провайдера. Сервер обрабатывает результат аутентификации и управляет пользовательской сессией.

Функции управления командами и каналами реализуются на стороне сервера через REST API. Клиент отвечает за ввод и отображение данных.

Функции обмена сообщениями реализуются через совместную работу нескольких компонентов: клиент отправляет запрос, сервер сохраняет сообщение в PostgreSQL, затем рассылает события другим клиентам через WebSocket. Для файлов дополнительно используется файловое хранилище.

Функция поиска использует отдельный компонент OpenSearch. Сервер записывает сообщения в БД и индексирует их, а поиск выполняется по индексу.

Таким образом, большинство функций реализуется через Mattermost Server, который взаимодействует с БД, файловым хранилищем, поисковым индексом и внешними сервисами.

---

#### Сопоставление информационной архитектуры и архитектуры данных

Основные информационные объекты системы: пользователь, команда, канал, сообщение, файл, сессия и настройки.

Объект «пользователь» реализуется структурами `User`, `Session` и `Preference`. Пользователь хранится в БД, сессии и настройки связаны с ним через `user_id`.

Объект «команда» реализуется через `Team`, а участие пользователей — через `TeamMember`.

Объект «канал» реализуется через `Channel`, а участие пользователей — через `ChannelMember`.

Объект «сообщение» реализуется через `Post`, который содержит ссылки на пользователя и канал. Треды реализуются через поле `root_id`.

Объект «файл» реализуется через `FileInfo`, где хранится метаинформация, а сами файлы размещаются во внешнем хранилище.

Сообщения хранятся в PostgreSQL и дополнительно индексируются в OpenSearch для поиска.

Таким образом, каждому информационному объекту соответствует одна или несколько структур данных, а связи между объектами реализуются через идентификаторы.

## Вопросы

### 1. Почему для анализа был выбран именно Mattermost, если он в первую очередь является корпоративным мессенджером, а не классической системой управления задачами?

Mattermost был выбран потому, что он автоматизирует реальные бизнес-процессы внутри организации, связанные с корпоративной коммуникацией, обменом информацией, согласованием действий и управлением доступом. В системе есть четко выделяемые акторы, информационные объекты и повторяемые процессы, которые можно формализовать с помощью UML-диаграмм. Кроме того, Mattermost подходит для архитектурного анализа, так как имеет открытый исходный код, понятную клиент-серверную архитектуру и хорошо выраженную модель данных. Это позволяет связать процессы пользователей с программными компонентами и структурами данных, что напрямую соответствует требованиям лабораторной работы.

### 2. Почему в системе отдельно выделены команды и каналы, нельзя ли обойтись чем-то одним?

Команды и каналы выполняют разные роли. Команда — это более крупная единица, которая объединяет пользователей и задает границы доступа. Каналы существуют внутри команды и используются для разделения общения по темам. Такое разделение позволяет лучше управлять доступом и структурировать информацию. На уровне данных это отражается в том, что канал связан с командой через `team_id`.

### 3. Почему сервер Mattermost можно считать stateless, если в системе есть сессии и WebSocket-соединения?  Почему важно сохранять stateless архитектуру
  
Сервер считается stateless, потому что основное состояние системы (пользователи, сообщения, каналы) хранится во внешних хранилищах, а не в памяти сервера. Сессии и WebSocket — это временное состояние, которое может быть восстановлено. Это позволяет масштабировать систему горизонтально, запуская несколько экземпляров сервера. Stateless важен, так как это позволяет горизонтально масштабировать приложение

### 4. Почему в системе используется отдельный компонент для поиска (OpenSearch)?

Поиск по тексту сообщений требует быстрого анализа большого объема данных. Реляционная база данных не оптимизирована для полнотекстового поиска такого уровня. Поэтому используется отдельный компонент, который хранит индекс сообщений и позволяет быстро выполнять поисковые запросы. При этом основное хранение данных остается в базе данных.

### 5. Как обеспечивается согласованность данных между PostgreSQL и OpenSearch? Может ли возникнуть рассогласование?

PostgreSQL является основным хранилищем (source of truth), а OpenSearch — вторичным индексом, который обновляется асинхронно. Это означает, что запись сначала фиксируется в БД, а затем отдельно отправляется на индексацию.

Индексация выполняется не в рамках одной транзакции с БД, поэтому в момент времени возможна временная рассогласованность:
- сообщение уже сохранено в PostgreSQL, но еще не попало в индекс;
- сообщение обновлено или удалено, но индекс еще не обновлен.

На практике это означает, что:
- сообщение может не находиться через поиск сразу после отправки;
- в редких случаях поиск может вернуть устаревшие данные.

Для снижения таких ситуаций сервер:
- отправляет события индексации сразу после изменения данных;
- использует механизмы повторной индексации при ошибках;
- поддерживает возможность полной переиндексации из БД.

Если происходит сбой (например, OpenSearch недоступен), данные в PostgreSQL остаются корректными, а индекс может быть восстановлен позже. Таким образом, система допускает временную несогласованность, но гарантирует восстановление согласованного состояния за счет повторной индексации.
