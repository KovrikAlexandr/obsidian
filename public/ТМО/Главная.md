Входные данные:

	- Высокоприоритетные заявки
	- Низкоприоритетные заявки
- Интенсивность обслуживания
- Тип приоритета: абсолютный (высокоприоритетные заявки обслуживаются в первую очередь)

#### 5. Сеть массового обслуживания
Исследовать характеристики сети массового обслуживания, в которой агенты (каналы обслуживания) могут подключаться и отключаться в произвольные моменты времени, с использованием методов имитационного моделирования.





В реальности процесс выглядит так:
1. Клиент пишет json лог (обязательные поля timestamp – время, group – группа это логическая единица в тенанте, system – имя сервиса в группе, level (info, warning, error) – вид лога) в logs-collector по REST API (возможна запись как одной json строки, так и батча)
2. logs-collector, приняв лог по REST API, пишет его как событие в один из брокеров Kafka
3. Из Kafka логи вычитывает сервис Fury. Он поднимает N потоков-воркеров в зависимости от количества групп и их квот (этот момент мы вряд ли будем использовать в модели)
4. Furry валидирует json строку (есть все обязательные поля) и записывает лог в кластер Opensearch


### Лаба 1 — M/M/1/0

- logs-collector без буфера (если перегруз — отказ)


### Лаба 2 — многоканальная с ожиданием (M/M/n, очередь ∞)

**Fury с N воркерами**

- λ — поток логов из Kafka
- μ — скорость обработки одного воркера
- n — число воркеров
- очередь — Kafka (считаем бесконечной)

### Лаба 3 — M/M/1/m (ограниченная очередь)

**Kafka как ограниченный буфер + один обработчик (Fury)**

- очередь ограничена размером m (например, retention / partition capacity в модели)
- при переполнении — потеря логов
- один consumer

### Лаба 4 — приоритеты

Разделить логи по `level`:

- error — высокий приоритет
- info/warning — низкий
- абсолютный приоритет → error всегда обрабатываются первыми
